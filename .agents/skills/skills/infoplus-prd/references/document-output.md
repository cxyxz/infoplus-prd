# 文档与输出经验

## 输出目录与隔离

默认正式目录为 `output/<流程编号>/`。显式 `--output-dir` 时，该目录是本次独立正式成果目录，例如 `output/Z1775workbuddy/`；不覆盖编号目录，也不在结束时自动移动。缓存、截图、Word、报告归属同一根；对比任务只读访问原版。`_verification` 只作临时工作区，不能当交付目录。

## Word 占用与原子替换

先写同目录 `.pending`，检查 ZIP 头和 `word/document.xml`，再尝试原子替换。遇到 `EBUSY`/`EPERM`/`EACCES` 时保留原文件和临时文件，明确报告“正式文件未更新”；用户解除占用后重跑 `generate`，程序应复用缓存，不重新分析业务数据。禁止先删原文件再复制；成功后清理本次临时文件。

## 单文档交付

V1.3 默认只生成 `流程编号：流程名称需求文档.docx`。技术分析继续保存在 Markdown、JSON、CSV、XSN、Workflow、截图和报告中。正文固定九章：业务概述、前置业务与数据关联、完整业务流程、流程节点与办理角色、表单字段清单、核心办理节点图文说明、业务分支与流转规则、待确认事项、附录。

已知文档缺陷及处理：章节必须自动编号且固定顺序；节点按 Workflow 正向拓扑排序，退回循环和并行关系单独说明；通用只读字段集中列示，节点只写新增、可编辑、必填和状态变化；字段类型按业务组件；按钮按动作 ID 去重；长图分段保持可读；历史阻断若后续已解决不再写为当前问题；同一待确认只保留一次。正文不放接口 JSON、脚本源码和无业务意义的节点 ID。

## 字段原子化

V1.3.1 发现多个独立字段被写入同一个「字段名称」单元格，并共享字段类型、必填和阶段。根因是 `src/business-content.mjs` 的 `businessFields()` 在分组后用 `mergeEquivalentFields()` 按「类型 + 规则」合并行，再由 Word 生成器按拼接文本反查字段。分组被误当作压缩字段数量的依据，导致字段 ID 丢失。

正确处理：以真实 field ID 为身份，建立原子字段记录（`src/field-atomic.mjs`）。分组只是属性，所有字段型表格统一输出「分组 | 字段名称 | 字段类型 | 必填 | 出现阶段 | 数据来源/规则」，一个字段一行。同一 ID 跨阶段可汇总，但每阶段必填、只读、显隐和来源必须单独保留。不同 ID 即使名称、类型、规则、阶段完全相同也不合并；同名不同 ID 未核实前分别保留。

禁止行为：按顿号、逗号、冒号或换行拆分旧单元格文字来反推字段边界；用相同分组或相同类型解释字段数量减少；为了缩小表格把多个字段放回一个单元格。缺少可靠身份时写待解析项。

验证方法：核对原始字段 ID 数、标准化字段记录数和 DOCX 字段表行数；检查每个字段名称单元格只有一个真实字段；检查同一 ID 跨阶段规则和不同 ID 同名记录是否被正确保留。回归测试使用 `scripts/inspect-docx.mjs` 实际读取 DOCX 的 `word/document.xml`，不仅检查中间 JSON。

## 验收

检查默认与显式目录都只生成一份 Word；运行测试、输出冒烟、版本一致性、保护基线；渲染后核对章节顺序、节点顺序、表格、图片、裁切和空白页。正式目录中的最新文件是唯一成果。
