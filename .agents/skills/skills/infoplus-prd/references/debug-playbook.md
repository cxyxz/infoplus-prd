# Debug 执行决策手册

本手册把历史问题转成顺序决策。先读 [问题索引](issue-index.md)，按症状进入对应条目。普通操作问题只做有限可恢复重试；不要一遇到未知问题就重写 Skill 或新建大量实例。

## 启动前

1. 输入 `流程编号` 或带编号标题，核对目标版本和已有缓存；缓存版本/定义 ID 不同则停止合并。
2. 先读 `README.md`、本手册和相关知识条目，再检查专用 Chrome、Debug 授权范围和已有实例。
3. 静态资料（Workflow/XSN/Views/字段）先保存；动态验证失败不能抹去静态证据。
4. 判断模式：IDE Debug 入口 + DEBUG 实例列表 + 页面调试标记 + 定义/版本/实例 + 当前身份全部吻合，才能进入 Debug 办理。否则前台只读或离线。

## 通用办理循环

进入节点 → 核对实例/身份/权限 → 全页面字段扫描 → 采集按钮 → 填合规测试数据 → 提交 → 分类弹窗与业务响应 → 核对真实后续待办 → 截图与字段/按钮关联 → 保存进度 → 切换下一身份。普通确认按授权处理；未知、删除、部署、配置变更不自动确认。

## 提交失败

1. 先判断是否为字段校验：检查消息和控件真实状态。
2. 是校验：保存提示 → 关闭提示（不等于成功）→ 修复字段 → 重新扫描 → 再提交；错误指纹不变两次则停止该动作。
3. 是业务关联错误：检查前置流程、真实业务编号、申请人和 Debug 身份；参考 [跨流程关联](cross-flow-identity.md)。
4. 是外部接口错误：保存脱敏响应、HTTP/errno 和当前节点；有限恢复，不循环刷新“制作中”。
5. 结果未知：先 `debug-session verify/observe` 检查实例和待办；状态未变化前不重复提交。
6. 停止当前动作后，继续其他可完成的节点和静态分析。

## 无法进入审批节点

顺序检查：当前真实待办 → 当前模拟身份 → 是否为 DEBUG 实例 → 页面可执行权限 → Workflow 进入条件 → 上一动作真实结果。只有五项证据齐全才切换身份；权限不足时按节点角色重新选择有权限身份，不绕过平台限制。仍失败则记录节点、待办、身份、条件、响应和截图，标为阻断。

## 无法获取完整截图

检查 iframe 与内部滚动容器 → 定位 `#form_holder` → 展开完整内容并测量宽高 → 检查横向裁切 → 必要时按业务模块裁剪 → 仍失败则记录缺失，不用视口外壳、错误提示或 XSN 预览冒充。详见 [截图质量](field-button-screenshot.md#截图质量)。

## 多路径与完成状态

优先完成一条代表性正常路径。互斥动作使用独立 Debug 实例；每个实例关联 path-plan、动作、真实后续节点和证据。按实例区分正式结束、主要审批完成、等待业务材料、外部服务阻断、表单校验阻断、当前分支未验证。Workflow 连线只提供候选映射，不是已实测路径。

## 中断恢复

先查 `raw/debug-runs.json`、`flow-progress.json`、`debug-session <目录> <实例ID> observe` 和已有截图索引，恢复实例 ID、节点、办理身份、最后成功动作与提交状态。旧记录无实例 ID 时必须与当前待办核对。不要新建相同实例，不要把另一个模型正在操作的实例当自己的证据。多人/多模型同时操作时，同一时间只允许一个控制者操作相同 Chrome 会话和实例。

## 未知问题

先按关键词匹配 `issue-index.md` → 检查代码和现有测试 → 执行有限次可恢复操作 → 保存现场和新失败原因 → 只有确认通用规律才回写知识库。业务特殊规则写入流程专属证据或配置，不写通用策略。

## 验收前检查

输出节点采集完成度检查表：节点识别、字段实测/XSN 补充、节点专属差异、全部按钮、按钮到目标节点映射、代表性路径、未验证分支、截图来源。Word 已生成不等于完成；未实际执行的节点/按钮不能标实测。
