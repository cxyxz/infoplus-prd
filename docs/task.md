# 开发任务：InfoPlus 旧流程自动采集与需求文档生成工具

## 一、项目背景与目标

我正在将浙江大学旧版 InfoPlus 流程平台上的业务流程迁移到新的流程平台。

旧平台是 InfoPlus IDE，我已经在 Windows 的 Chrome 浏览器中登录，并且具备查看相关流程及表单配置的权限。

此前我通过 Chrome DevTools 的 Network 获取流程定义、表单模板等接口数据，再结合 `.xsn` 文件手动分析业务逻辑，最后编写新平台重建需求文档。

现在需要把这一套工作实现为**可重复使用的自动化工具，并封装成 Codex Skill**。

最终希望只需要告诉 Codex：

> 使用 $infoplus-prd，分析 Z0095：教职工因公临时出国、赴港澳审批，生成新平台重建需求文档。

Codex 就能够自动读取对应流程，采集完整数据，分析业务规则，生成流程图、表单图片、字段表和需求说明书。

注意：**这是一个通用工具，绝对不能只针对 Z0095 硬编码实现。**

## 二、总体技术架构

建议使用：

- TypeScript / Node.js：流程采集、接口处理及数据标准化。
- Playwright MCP：连接浏览器并执行页面操作。
- Python：必要时进行 XSN 解包、XML/XSL 解析、图片处理及 DOCX 生成。
- Codex Skill：编排整个工作流程，提供自然语言调用入口。
- 本地目录：保存采集资料、缓存、分析结果和生成文档。

优先研究 Playwright MCP 的浏览器扩展模式：

`npx @playwright/mcp@latest --extension`

尽量复用用户已经登录 InfoPlus 的 Chrome 标签页。

如果该方案受限，可以考虑其他安全可靠的浏览器连接方式，或者开发一个最小化 Chrome 扩展配合本地采集程序。

不允许通过读取 Chrome Cookie 数据库、导出登录凭据或绕过系统认证实现。

项目必须可以在 Windows 环境下运行。

## 三、第一部分：InfoPlus 平台自动采集

### 1. 流程定位

支持输入：

- 流程编号，例如 Z0095。
- 流程完整名称。
- 流程名称关键词。
- 已知流程定义 ID。

自动在 InfoPlus IDE 的项目树或查询接口中寻找对应项目。

需要识别：

- 项目编号与名称。
- 流程编码及流程名称。
- 流程定义 ID。
- 表单模板 ID。
- 项目版本及版本更新时间。
- 发布版本与历史版本。
- 关联视图列表。

默认优先分析当前正式使用的版本。若无法判断正式版本，应明确告知，不得随意选择历史版本。

### 2. 流程定义采集

我通过 Chrome Network 观察到一个接口，形式类似：

`findWorkflowDefinition?workflowDefinitionId=6092962e-42ac-11f1-af63-005056838980`

这只是截图中的示例，请先通过真实浏览器验证完整 URL、请求参数和响应结构。

目标是完整获取工作流定义，包括：

- 所有节点及节点类型。
- 节点名称和业务含义。
- 审批节点及处理人配置。
- 自动处理节点。
- 条件判断与分支表达式。
- 连线及 source/target 关系。
- 退回、重新提交、结束等流转关系。
- 节点对应表单视图。
- 节点关联的权限、动作、配置。
- 自动步骤中能够识别的业务规则。
- 原始流程图节点布局坐标。

不要仅获取流程截图，优先保存完整结构化数据。

需要自动识别流程中的并行分支、合并节点、条件网关、循环退回和特殊结束路径。

对于无法确定语义的脚本或表达式，保存原文并标注待确认，禁止猜测。

### 3. 表单定义采集

我还观察到：

`findFormTemplate?templateId=80c4f9aa-04c1-4e35-a255-42de25401b85`

接口返回的字段对象包含类似：

- groupName
- fieldName
- repeatDepth
- fieldType

需要自动解析完整字段定义，而不是只读取截图当前展示的部分。

提取：

- 字段名称和字段标识。
- 字段数据类型。
- 所属字段组。
- 重复明细组结构。
- 默认值。
- 枚举选项。
- 校验条件。
- 是否必填。
- 是否只读。
- 相关业务规则。

注意：接口中的原始字段不一定全部是用户可见的表单控件，需要结合表单视图进一步判断。

### 4. 全部阶段视图采集

这是项目的重点。

InfoPlus IDE 左侧 Views 中存在大量视图，例如：

- 00主表单
- 00欢迎页
- 01选择页面
- 02填写
- 03统一审核
- 03统一审核（国合处初审）
- 04所在单位选择
- 05党委确认行前出访（机关）
- 06修改表单
- 申请人打印表
- 其他阶段视图

以上仅为示例，真实采集时必须动态获取全部视图，不能写死列表。

针对每个视图：

1. 获取视图名称、ID 和所属流程版本。
2. 查找实际的视图数据接口，例如截图中出现的 `views` 请求。
3. 保存原始视图定义，包括 HTML、CSS、XML、XSL 或其他实际使用的格式。
4. 获取关联的图片、样式等依赖资源。
5. 分析视图中使用的表单字段和控件。
6. 判断该视图关联的流程节点。
7. 尝试使用真实页面或兼容渲染方式还原完整界面。
8. 输出对应的 PNG 图片。
9. 保存视图与流程节点之间的映射关系。

不同阶段可能共用同一视图，必须记录复用关系，避免重复生成无意义的图片。

欢迎页、审批页、申请页、打印页需要分别识别。

**不能因为获取了主表单就认为已经获得全部阶段表单。**

优先真实采集，不能根据视图名称虚构页面布局。

### 5. XSN 文件采集和解析

之前我还获取过不少 InfoPlus 表单的 `.xsn` 文件。

工具需要同时支持：

- 从已授权的平台页面发现并下载实际提供的 XSN 文件。
- 批量导入本地已有的 XSN 文件。
- 对 XSN 自动解包与解析。
- 关联对应的表单视图。
- 尝试还原表单图片。

XSN 是基于 CAB 的表单模板包，可能包含：

- manifest.xsf
- XSD
- XSL
- XML
- 图片及其他资源
- 脚本或编译文件

需要基于这些资料提取：

- 完整字段结构。
- 字段与控件绑定关系。
- 页面布局。
- 不同视图使用的字段。
- 显隐和校验规则。
- 重复表格结构。
- 可识别的交互行为。

静态 XSN 图片只能代表某种默认状态，动态显示、权限和必填规则应结合流程配置及其他证据确认。

不得执行来源不明的模板脚本或二进制程序。

如果平台没有提供 XSN 下载方式，不允许编造接口。可以依赖在线视图数据，或要求导入现有文件。

## 四、第二部分：结构化分析引擎

采集到的数据需要先进行标准化，再生成文档。

建立统一数据结构：

1. Project：项目信息与版本。
2. Workflow：流程定义。
3. Node：流程节点。
4. Transition：连线和条件。
5. Actor：审批人员或组织规则。
6. Form：表单定义。
7. Field：字段定义。
8. View：阶段视图。
9. Rule：业务规则。
10. Evidence：来源证据与待确认事项。

每项业务规则都应尽可能记录来源，例如：

- 来源接口及数据路径。
- 所属节点。
- 对应视图。
- 原始条件表达式。
- 文件名称。
- 是否已确认。

分析时重点识别：

- 申请人如何发起。
- 申请人身份或类型选择。
- 不同申请类型对应的流程。
- 审核人如何确定。
- 条件分支如何判断。
- 是否根据天数、金额、身份等指标自动分流。
- 退回后由谁修改。
- 是否重新审核。
- 申请人能否撤销。
- 自动处理的业务作用。
- 流程如何结束。
- 是否存在后续关联流程。

应保留完整原始数据，但需求文档需要转化为业务语言。

例如：

技术数据：`durationDays > 60`，下一节点为某审批部门。

需求语言：当申请天数超过 60 天时，须提交指定部门审核。

**最终文档面向新平台开发人员，而不是要求他们照搬旧 InfoPlus 的内部实现。**

## 五、第三部分：需求文档自动生成

### 1. 文档定位

生成一份精炼、准确、完整的新平台流程重建需求文档。

正文建议控制在 4～8 页左右；复杂表单、流程图和原始字段清单可放到附录。

不要生成冗长、空泛的系统设计说明书。

文档至少包含：

**第一章：流程概述**

说明业务用途、适用对象、流程目标和重建范围。

**第二章：业务流程**

提供完整流程图，以及分支、审批、退回、自动处理和结束规则。

复杂流程可以同时生成完整流程图和简化业务流程图。

**第三章：表单需求**

描述申请表、审批表、修改表等不同阶段的页面和字段。

表单字段必须采用表格，至少包括：

| 字段名称 | 字段类型 | 必填 | 适用阶段 | 备注 |
|---|---|---|---|---|
| 申请人 | 成员选择 | 是 | 申请 | 自动带出 |
| 所在单位 | 组织选择 | 是 | 申请 | 根据人员信息 |
| 申请日期 | 日期 | 是 | 申请 | 日期选择 |

上表只是格式示范，不能当成旧平台的实际字段。

字段类型应尽量转化为新平台开发人员理解的类型，例如单行文本、多行文本、数字、下拉选择、单选、复选、成员、组织、日期、日期区间、附件、子表单等。

**第四章：审批与业务规则**

明确审批节点、审批对象、条件分流、退回和重新提交等逻辑。

**第五章：特殊规则**

描述自动计算、动态显隐、字段联动、办理后续动作等实际存在的业务需求。

**第六章：待确认事项**

列出无法从旧平台数据明确判断的问题。

不要虚构需求填补空缺。

### 2. 流程图

根据真实工作流定义自动生成：

- 完整流程图 PNG。
- 完整流程图 SVG。
- 可修改的 Mermaid 文件。
- 如有必要，附一张简化业务流程图。

要保留所有实际流程分支、判断条件和退回关系。

原始节点坐标可以用于还原参考，但也可以重新排版以提高可读性。

### 3. 表单图片

为每个实际业务阶段生成清晰的页面图片。

按阶段命名，能够对应文档中的节点和字段表。

完整表单图放入附录，重复图片去重。

如果无法准确还原，只输出源页面截图并标注限制，不要伪造原界面。

### 4. 文件格式

至少生成：

- requirements.md
- requirements.docx
- workflow.png
- workflow.svg
- workflow.mmd
- fields.xlsx 或 CSV
- views/ 下的阶段图片
- raw/ 下的原始数据
- normalized/ 下的结构化 JSON
- analysis-report.json：采集完整性和待确认项

需要支持重复生成，避免每次都重新分析全部数据。

## 六、第四部分：开发 Codex Skill

创建技能：

`.agents/skills/infoplus-prd/SKILL.md`

Skill 名称：

`infoplus-prd`

必须支持：

- 输入编号分析流程。
- 输入名称查询流程。
- 自动调用采集程序。
- 使用已有缓存。
- 解析新增 XSN 文件。
- 自动执行业务分析。
- 生成最终需求文档。
- 对缺失数据给出明确报告。

推荐调用方式：

`$infoplus-prd 分析 Z0095，并生成新平台流程重建需求文档`

同时提供独立命令行方式，例如：

`infoplus-prd scan Z0095`

`infoplus-prd analyze Z0095`

`infoplus-prd generate Z0095`

命令只作目标示例，具体可按照最合适的项目结构实现。

Skill 应当可以从其他 Codex 项目中复用，不依赖当前对话上下文。

## 七、数据缓存与完整性校验

首次执行时采集完整资料，后续优先复用本地数据。

必须按流程编号、版本和资源类型建立缓存。

自动检查：

- 流程定义是否完整。
- 节点与连线是否全部解析。
- 是否存在无法解释的分支。
- 视图总数与已采集数量是否一致。
- 是否存在缺失的表单资源。
- 字段是否有未识别的类型。
- 业务规则是否有未确认项。
- 页面截图是否成功。
- 需求文档中的内容是否有来源。

如果缺失关键数据，应明确指出缺失项，不得宣称采集成功。

支持单独重新抓取失败的资源。

采集期间只允许执行已授权的只读操作，不得修改或发布旧平台的流程配置。

所有账号凭据、会话密钥和敏感请求头均不得写入日志、导出文件或提交 Git。

不向第三方服务自动上传业务数据。

## 八、实施步骤

请直接开始开发，不要只停留在架构建议。

按照以下顺序推进：

**阶段一：平台探查**

检查现有开发环境和可用浏览器连接能力。

基于当前登录的 InfoPlus 页面，识别项目列表、流程定义、表单模板和视图接口。

先实现一个流程的真实采集闭环。

对于不能确认的接口，必须进行实际验证。

**阶段二：数据采集**

实现项目定位、流程获取、表单获取、视图获取、文件下载与本地缓存。

**阶段三：解析引擎**

实现工作流图结构解析、字段解析、XSN 解析、规则提取和阶段映射。

**阶段四：文档生成**

实现 Markdown、DOCX、字段表、流程图和视图图片的输出。

**阶段五：Skill 封装**

编写 SKILL.md、必要的运行脚本、Windows 安装说明及使用示例。

**阶段六：测试验收**

优先使用 Z0095 进行端到端测试。

确保：

1. 能通过编号准确定位项目。
2. 能获取实际工作流完整定义。
3. 能枚举并采集全部阶段视图。
4. 能得到完整字段清单。
5. 能生成与真实节点关系一致的流程图。
6. 能生成真实表单截图或可追溯的还原图。
7. 能输出精炼的新平台需求文档。
8. 不能确认的条件不会被编造。
9. 换一个流程编号无需修改核心代码。
10. 发生失败时能够说明原因并支持重试。

对于目前不能访问浏览器、缺少文件或没有足够权限的情况，请明确记录阻塞原因，先完成可离线测试的模块，不要使用模拟数据冒充真实采集结果。
